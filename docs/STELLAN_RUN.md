# Stellan-Run in the desktop app

New desktop packages use our independent C++ Stellan-Run engine by default. The app’s authenticated loopback adapter runs inside its existing Node backend, with no extra Node inference process. The native worker receives prompt IDs through private stdin and emits bounded JSON events. Model text is never placed on command lines. Stop cancels generation; the next request can reopen a verified worker and resend its prompt. Idle workers rest and release their model mappings.

Activated models keep the existing AES-GCM unlocking flow. Only the small first split is decrypted into the private temporary directory. Both GGUF splits are SHA-256 checked, mapped separately and combined through tensor views without copying the complete model or expanding its weights. Linked single-file GGUFs remain supported. The ID-only native service reads the end-token metadata directly, avoiding an unused second tokenizer lookup table; our JS tokenizer performs text encoding.

The sidebar keeps normal context small and offers Long context explicitly. Lite uses a bounded32-token prefill buffer and fixed recurrent state; Max uses lazy Q8 KV chunks in the app. Two CPU workers are used. Exact evaluated prefixes can be reused; earlier-state disk snapshots are unavailable, so a changed prefix or model swap may require rereading the conversation.

Current limits: CPU inference only; no native GPU backend, speculative decoding, or enforced token grammar. The API reports these capabilities explicitly. The app validates tagged tool responses and retains mandatory approvals, sandboxing, local note isolation and offline activation. Full Max-weight/device validation remains outstanding. Tiny model fixtures cover both architectures and locked split inference; historical HumanEval scores still refer to the previous llama.cpp evaluator, not a new Stellan-Run score. Raw runtime comparisons include unfavorable results and rejected optimizations.

For migration, packages retain the historical `llamaRelease` manifest field and a legacy `llama-server` filename containing the same Stellan-Run executable. This alias lets older updater versions validate the new package; the app selects `bin/<platform>/stellan-run` through its verified runtime marker. Desktop workflows build our C++ source and require a real Lite tool exchange before publication. Main releases keep the existing private draft and signed-update-host behavior.

Native backend host and original MCP client improvements are merged into main. The native host is an inference service prototype; files, authenticated app services, approvals and updates still need further native migration. The MCP client has original bounded protocol, initialization, stdio framing and request lifecycle code; SDK HTTP/SSE transports and operation-result schemas remain.

Lite startup uses the app’s 7 GiB reported-memory floor for nominal 8 GB computers, including public Apple Silicon runners. This is a total-memory check, not a promise of enough free memory; Max retains its separate runtime guard. Release checks still run real inference and a complete tool exchange on every platform.

The portable quantized batch fallback unpacks each weight block once per batch and shares it across activation vectors, preserving the previous per-vector floating-point accumulation order. This removes repeated unpacking on CPUs without the x86 SIMD path, without an expanded model copy. Independent forced-scalar and accelerated fixtures cover both Q4/Q6 and partial batches; no physical ARM throughput number is claimed.
