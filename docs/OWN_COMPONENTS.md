# Components we can make our own

This is a prioritized engineering proposal based on the current source and dependency manifests, not a claim that removing a library automatically improves speed. Keep interoperability, credits, licenses and working integrations. Replace a component only when our implementation passes its compatibility checks and earns its maintenance cost.

| Priority | Current component | Original Locali Labs replacement | Benefit to measure | Completion condition |
| --- | --- | --- | --- | --- |
| 1 — app default, qualification continues | llama.cpp / ggml in the portable app | Stellan-Run execution, scheduler, cache, serving and CPU/GPU kernels | First-token latency, decode throughput, CPU time, total peak RAM and idle load | Both actual Lite/Max checkpoints; physical Mac/Windows/Linux; current app settings; agent-task parity; grammar, encrypted/split models, activation, cancellation and packaging |
| 2 — follow the engine | llama.cpp's tokenizer and chat-format execution | Our audited SentencePiece/Tekken readers, prompt formatter and tool-output constraints | Correct token IDs, lower startup overhead, dependable tool calls | Golden multilingual/code/special-token cases against both exact release tokenizers; complete tool exchanges and malformed-output handling; never silently change tokenization |
| 3 — staged | MCP SDK transports/schema runtime (`@modelcontextprotocol/sdk`) | Complete our existing `McpRpc` and `McpProcessTransport` with original bounded validators and HTTP/SSE transports | Bundle size, connection startup, idle RAM and reliability | Supported negotiated protocol versions, session lifecycle, authorization, redirects, streaming, cancellation, reconnects and malformed/untrusted responses; preserve tool approvals |
| 4 — small scope | `cross-spawn` in MCP process startup | Our supervised executable resolver/launcher on top of OS or Node process APIs | Dependency/bundle reduction and reliable process cleanup | Windows PATH/PATHEXT, `.cmd`, argument escaping, Unicode/spaces, explicit environments, process-tree cleanup and POSIX behavior; never introduce unrestricted shell execution |
| 5 — separate prototype | Node.js portable backend host | Small native Stellan host for session control, local API, files, approvals and private memory | Idle RSS, startup, package size and integration reliability | Migrate service by service; preserve authentication, CSP, updates, GitHub sign-in, tools, sandbox and all approval boundaries. Do not build a new JavaScript engine |
| 6 — optional, high effort | Tauri desktop wrapper | Our own thin platform shell over the existing OS webviews | Install/startup size, idle RAM and desktop behavior | Native installers, window lifecycle, signing, accessibility, file dialogs, deep links and updates on every platform; use OS webviews rather than writing a browser engine |
| 7 — only with a narrow scope | `unpdf` PDF-text extraction; DOCX extraction using `fflate` | An original bounded document-to-text service | Extraction correctness, worker RAM and startup | Representative real files, fonts/encodings, malformed inputs, decompression limits, timeouts and resource isolation. Start with plain/text formats; keep the mature PDF fallback until parity |
| 8 — low priority | `yaml` skill frontmatter and `ignore` workspace matching | A deliberately limited frontmatter reader or exact Git-compatible matching | Actual shipped bytes and maintenance cost | Preserve accepted existing skill files and nested ignore/negation semantics. A hand-written glob or split-on-colon parser is insufficient. Changing formats requires an explicit migration |

The agent loop, context budgeting, bounded per-chat memory, tool approvals, sandbox integration and much of the MCP request/process lifecycle are already our code. Improve those directly; do not describe them as new third-party replacements. Ollama is an optional terminal backend; routing that client to Stellan-Run becomes possible after the serving and compatibility work above. Keep it as a working option until then.

The separate native-host branch now runs verified Lite inference directly in C++, with private pipe controls, bounded input buffers and idle process unloading. It remains an inference prototype; the app's authenticated API, files, approvals and other services still need migration. The separate MCP branch owns bounded wire/initialization validation, stdio framing and in-flight resource budgets. Isolated import/framing measurements show component-level improvements; whole-app savings and complete SDK/backend replacements remain unestablished. These projects preserve separate branches while inference correctness and performance remain the priority.

Keep standard cryptography, OS security facilities, ZIP/compression compatibility, compilers, TypeScript and test tooling unless a separate measured need justifies replacing them. Do not implement custom cryptographic algorithms or an entire browser/JavaScript engine to reduce dependency count. Base-model weights remain attributed foundation models; an original runtime does not make their training or licenses our own.

## Source and compatibility references

- Local manifests: `package.json`, `src-tauri/Cargo.toml` and the pinned llama.cpp build in `.github/workflows/desktop-platform.yml`.
- Existing original MCP code: `src/portable/mcp-rpc.ts`, `src/portable/mcp-process.ts`. The SDK is still used for transports and protocol/schema definitions.
- [Node process documentation](https://nodejs.org/download/release/v24.22.2/docs/api/child_process.html): Windows batch/command files require special launching behavior. Replacing cross-spawn needs that compatibility, not simply changing the import.
- [MCP specification](https://modelcontextprotocol.io/specification): check each version we negotiate; a new transport must preserve protocol and authorization behavior.
- [Tauri architecture](https://v2.tauri.app/concept/architecture/) and [process model](https://v2.tauri.app/concept/process-model/): the current wrapper already uses OS webviews. A bespoke shell has to earn its additional platform maintenance.

No dependency removal, production switch, hosted evaluation or paid infrastructure is triggered by this roadmap.
